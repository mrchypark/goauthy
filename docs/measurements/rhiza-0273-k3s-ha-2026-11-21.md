# Rhiza v0.27.3: local k3s HA functional check

Date: 2026-11-21 (Asia/Seoul). Source: GoAuthy commit `b2ea247b7dfa2b4d7f086d719b3c1bc9444a5fad`, with `github.com/mrchypark/rhiza v0.27.3`.

## Environment and scope

The existing `kiri` context pointed to k3s `v1.37.1+k3s1` on one ARM64 node. The client was `kubectl v1.35.3`, outside the supported one-minor-version skew. A dedicated `goauthy-ha-rhiza-check` namespace contained all Kubernetes test workloads. No existing namespace or cluster-wide resource was modified.

The test adapted `deploy/e2e-kv-ha`: the hard-coded namespace and service DNS names were changed for the fixture, the required node anti-affinity was removed because only one node was available, and the Versity storage claim was replaced by `emptyDir`. The GoAuthy executable was built from the source commit for Linux ARM64 and copied into each test Pod; the fixture used the curl container image to run that binary instead of the project's scratch image. Versity used the fixture's `versity/versitygw:v1.8.0` image. This is a functional single-node test, not a production HA deployment or an image qualification.

## Results

- Three GoAuthy Pods and the Versity Pod reached Ready. At the end of the recorded run all had zero restarts.
- The repository's `TestKVAPI` passed with `GOAUTHY_E2E_KV_PHASE=initial` against all three Pods. This includes writes, encrypted values, authorization checks, and reads through each Pod.
- `TestKVAPI` also passed with `GOAUTHY_E2E_KV_PHASE=state`, checking the resulting state through all three Pods. This phase was run without a restart and does not establish recovery after a fault.
- In an earlier setup run, one Pod restarted once during schema migration after a `QuePaxa quorum unavailable` / `node is not ready` error. It subsequently reached Ready. The cause was not established; the recorded KV run above did not reproduce a restart.

## Gaps

Chaos Mesh CRDs were absent. Installing them would change shared cluster-wide resources, which was outside the authorized scope. No fault injection, Pod replacement, quorum-loss experiment, recovery verification, node-failure test, or production-cloud qualification was performed. A single node cannot demonstrate resilience to node failure. The fixture's object store was ephemeral and is not evidence of durable disaster recovery.

## Cleanup

The test's port forwards were stopped. The dedicated namespace was deleted after checking its UID and deletion was confirmed. The test created no PVC; the cluster listed no PVs after cleanup. Temporary binary, credentials, test state, manifests, logs, and scripts were removed; ports 18080–18082 were not listening after cleanup. The pre-existing namespace names remained present.
