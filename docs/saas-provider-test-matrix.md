Assessed 2026-10-13 against the current managed-provider adapter and primary vendor documentation. Catalogue: **38 candidates = 28 OAuth + 3 optional hosted identity + 7 API-key**. Catalogue entries are not installed providers; the existing 32-active-provider quota remains unchanged.

**Live account-link PASS: Google and GitHub only**, from existing parent/human evidence. All other live checks are UNTESTED. GitLab login preparation is complete, but login/app registration/consent remain setup pending. **No real refresh PASS is established**: the one attempted GitHub UI refresh has an unknown outcome and must not be duplicated to resolve it. Synthetic success does not certify a live provider, refresh, consumer delivery, or production integration.

## Common contract and setup

Register an owned app, its confidential client credentials, and an exact allowed callback; confirm developer/test-user access, required product enablement and least permissions before consent. HTTP callbacks are limited locally to loopback; vendor acceptance still needs confirmation. A numeric-loopback requirement must match the application's configured origin/session, not just one callback field. Use HTTPS when vendor loopback eligibility is unresolved. Record only public configuration and stage outcomes, never credentials, account identifiers, codes, or provider response bodies.

Current managed OAuth sends an authorization code flow with S256 PKCE, explicit Basic or form client authentication, and form-encoded token requests. Identity is a bearer GET returning an HTTP200 JSON object with a **top-level string or canonical int64 subject**. No nested paths, custom identity headers, JSON token request, extra authorization options, separate refresh endpoint, or public-client mode is configurable. Granted scopes must be an exact space-separated subset; there is no comma parser. Only the exact GitHub authorization/token/identity triple plus `SubjectField=id` allows configured `[]` and absent/empty returned scope. Empty scopes are not a generic fallback.

Exact Google and GitHub profiles require their exact callback `iss` before consuming state; other profiles reject nonempty callback `iss`. A documented ID-token issuer alone does not establish callback behavior. These are OAuth account links through bearer identity reads, not general ID-token authentication. Session/state/replay, current authority, provider revision, generation, revocation, CAS, consumer/resource consent and public-IP/TLS/SSRF controls remain required. Refresh uses the same token URL and sends grant_type/refresh_token plus client authentication; extra refresh-expiry fields are not ingested. Local revocation does not revoke vendor tokens.

## Focused synthetic result and remaining live work

[New matrix](../internal/saas/oauth2_provider_matrix_test.go): six sequential local TLS cases, **PASS**, package time **3.567s** on Go1.27.2. Two compatible response combinations cover Figma's absent JSON scope/large string ID and Spotify's immutable account_id distinct from id. Four expected-rejection controls cover generic array scope, comma scope, absent form scope and nested identity; rejected responses install nothing, and callback replay makes no second request. These are six response cases, not six live-provider passes. Expiry and refresh are outside this new matrix; existing security/lifecycle tests are not duplicated per provider.

One focused invocation used `GOTOOLCHAIN=local GOMAXPROCS=2 GOPROXY=off GOSUMDB=off`, `go test -mod=readonly -p 1 -parallel 1 -count=1 -run '^TestOAuth2ProviderMatrixSyntheticLifecycle$' -v ./internal/saas`. No production logic changed, so these negative assertions are contract controls, not a production red/green fix. No additional full suite, race, performance test or live request was run.

Parent's next sequential live gate is app/account availability, then one consent/link attempt per eligible candidate. Record link and refresh separately. Public status has state/version but no refreshedAt or refresh-availability field; successful same-generation refresh increments version by one. Missing refresh token fails before claim/exchange and can leave unchanged ready/version. Ready text alone therefore cannot prove refresh, token freshness, or the outcome of a timed-out click. Use fresh public status metadata and an established version baseline; an unknown exchange is not retry permission.

Historical [Conductor readiness](conductor-saas-readiness.md) covers local synthetic flows, not these external providers. All unresolved vendor scopes, callback rules, app eligibility, token response shapes and current Meta documentation stay unresolved until supported evidence is available. No consumer grants/delivery are inferred from the GitHub public-ID link with `[]`.
