# 관리자 화면 사용 안내

이 문서는 관리자 대시보드, 사용자, 역할, 그룹, API 키, 세션, 이벤트, 이메일 템플릿, IP 차단 목록의 현재 화면 동작과 운영 절차를 설명합니다. 화면 문구나 API 동작이 배포 설정에 따라 달라질 수 있는 곳은 따로 표시했습니다.

## 시작하기 전에

- 관리자 권한이 있는 계정으로 로그인한 뒤 같은 브라우저에서 `/auth/v1/admin`을 여세요. 관리자 화면은 브라우저 세션과 같은 출처의 CSRF 토큰을 사용합니다. API 키의 `Authorization` 헤더로 관리자 화면에 로그인하거나 API 키를 관리할 수는 없습니다.
- 접근 가능한 화면과 변경 권한은 로그인 계정의 권한에 따라 달라집니다. 버튼이 보여도 서버 권한 검사를 통과하지 못하면 변경되지 않고 오류가 표시됩니다.
- 오른쪽 위 언어 선택에서 English 또는 한국어를 고를 수 있습니다. 작은 화면에서는 메뉴 버튼을 눌러 내비게이션을 펼치세요. 대시보드 카드와 상단 메뉴는 같은 관리 영역으로 이동합니다.
- 변경 요청이 진행되는 동안 제출 버튼이 잠기거나 진행 상태가 표시됩니다. 성공 메시지나 서버 응답을 확인한 다음 다음 작업으로 넘어가세요. 오류가 나면 입력값을 보존하는 폼에서는 내용을 확인하고 다시 시도할 수 있습니다.

## 대시보드

대시보드는 로그인 계정의 이메일을 표시합니다. 이메일이 없으면 기본 사용자 이름, 그것도 없으면 주체 ID를 표시합니다. `계정 설정` 링크는 `/account`로 이동합니다. 카드에서는 사용자·역할·그룹, 애플리케이션 설정, 운영 기능으로 이동할 수 있습니다. 대시보드는 `/account/data`를 읽어 신원 정보를 표시하며, 불러오기에 실패해도 관리 영역 링크는 사용할 수 있습니다.

## 사용자 관리

### 사용자 찾기와 편집

`Users`에서 이메일, 주체 ID, 마지막 로그인을 확인하고 행의 이메일을 눌러 상세 편집 화면을 여세요. 목록이 페이지로 나뉘면 `Next page`를 눌러 이어서 봅니다. 해당 페이지는 서버가 준 이어가기 토큰을 사용합니다. 사용자 목록에서 직접 검색하는 입력란은 없습니다.

편집할 수 있는 항목은 이메일, 이름, 성, 언어, 역할, 그룹, 계정 만료, 새 비밀번호, 생년월일·전화번호·주소·우편번호·도시·국가·시간대 같은 프로필 값, 계정 사용 여부, 이메일 확인 여부입니다. 역할과 그룹은 이름을 쉼표로 구분해 입력합니다. 빈 새 비밀번호는 기존 비밀번호를 유지합니다. 편집 폼에서 계정 만료를 비우면 만료가 해제됩니다. 저장하면 서버가 다시 권한과 입력값을 검증합니다.

### 사용자 추가

1. `New user`를 누릅니다.
2. 이메일을 입력하고 언어, 역할, 그룹을 지정합니다. 필요하면 기본 사용자 이름, IANA 시간대(예: `Asia/Seoul`), 계정 만료 Unix 초를 입력합니다.
3. `Create user`를 눌러 서버 응답을 확인합니다. 성공하면 계정이 생성되고 첫 비밀번호 설정 이메일이 발송됩니다.

만료값은 비워 두거나 `1719784800` 이상의 안전한 정수(Unix 초)를 입력해야 합니다. 계정 생성 API는 복구 서비스가 설정된 배포에서만 연결됩니다. 설정되지 않았으면 생성이 실패할 수 있으며 운영자가 해당 서비스를 구성해야 합니다. 이메일 발송 오류는 계정 생성 자체를 되돌리지 않을 수 있습니다. 사용자가 메일을 받지 못했다면 폼을 반복 제출하지 말고 메일러·복구 서비스 로그를 확인하고 운영 절차로 안내 메일을 처리하세요. 이 화면에는 재발송 버튼이 없습니다.

### 사용자 삭제

편집 화면에서 `Delete user`를 누르고 확인창에서 주체를 확인하세요. 삭제가 성공하면 사용자 목록으로 돌아갑니다. 이는 되돌리기 버튼이 있는 작업이 아니므로, 계정 비활성화나 세션 종료로 충분한지 먼저 운영 정책을 확인하세요.

## 역할과 그룹

`Roles`와 `Groups`는 각각 실시간 권한 서비스의 역할·그룹 목록입니다. 목록에서 이름과 변경할 수 없는 ID를 확인하세요. `New role` 또는 `New group`으로 추가하고, 항목 이름을 눌러 편집할 수 있습니다.

각 폼에서 이름과 선택 메타데이터를 입력합니다. 메타데이터는 비워 두거나 JSON을 입력하세요. 객체뿐 아니라 배열, 문자열, 숫자, 불리언, `null`도 백엔드 계약상 유효한 JSON 값입니다. JSON 문법이 잘못된 경우 화면에서 오류를 표시하고 저장 요청을 보내지 않습니다. 기존 엔터티의 ID는 수정할 수 없습니다.

이 화면은 역할·그룹 정의의 이름과 메타데이터를 관리합니다. 멤버십을 지정하려면 사용자 편집 화면에서 역할·그룹 이름을 입력하세요. 이 화면에는 역할별 세부 권한 정책을 편집하는 기능이 없습니다. 서비스의 RBAC 규칙이 각 역할과 그룹의 실제 권한을 결정합니다. 삭제는 확인 후 진행되며 기존 사용자·정책에 미치는 영향이 불확실하면 운영자와 먼저 확인하세요.

## API 키

### 새 키 만들기

1. `New API key`를 누르고 고유한 이름을 입력합니다.
2. 필요한 권한 그룹과 읽기·만들기·수정·삭제 권한을 선택합니다. 적어도 하나는 선택해야 합니다. 화면에는 그룹과 권한이 한국어로 표시되지만 서버로 보내는 그룹 식별자(예: `ApiKeys`, `UserAttributes`)와 권한 값(`read`, `create`, `update`, `delete`)은 고정된 원래 값으로 유지됩니다. 필요한 최소 권한만 선택하세요.
3. 만료 Unix 초를 입력하거나 비워 두고 `Create key`를 누릅니다. 만료값을 지정한다면 `1719784800` 이상의 안전한 정수여야 합니다.
4. 성공 결과에 표시된 비밀 값을 안전한 위치에 즉시 복사하세요. 비밀 값은 다시 조회할 수 없습니다. 복사를 마친 뒤 `Done`을 눌러 목록으로 돌아갑니다.

### 권한 변경, 교체, 삭제

- `Edit`에서는 키 이름을 바꾸지 않고 권한과 만료만 수정합니다. 만료를 비우면 만료를 해제합니다.
- `Rotate`는 같은 키의 비밀 값을 즉시 교체합니다. 성공 시 새 비밀 값을 한 번만 표시하므로 호출 중인 서비스에 반영하기 전에 화면을 떠나지 마세요. 기존 비밀 값은 새 값으로 바뀐 뒤 사용할 수 없습니다.
- 중단 없는 교체가 필요하면 기존 키를 바로 회전하지 말고, 새 이름의 키를 만든 뒤 소비자 설정을 바꾸고 새 키를 확인한 다음 이전 키를 삭제하세요.
- `Delete`는 확인 후 키를 폐기하고 목록을 새로 불러옵니다.

키 생성·수정·회전·삭제 UI는 브라우저 세션과 CSRF를 사용합니다. API 키 자체를 `Authorization` 헤더로 보내 키 관리 API를 호출하는 것은 지원되지 않습니다.

## 세션

`Sessions`에는 상태 필터와 행 수가 있습니다. 상태는 `Auth`, `Init`, `LoggedOut`, `Unknown` 중에서 고르고 `Apply`를 누르세요. 행 수는 1–65535의 정수입니다. 대량 결과에서는 서버가 페이지 크기를 적용하며 `Next page`가 나타나면 눌러 다음 페이지를 확인합니다. 표에는 주체, 상태, 마지막 확인, 만료, 원격 IP가 표시됩니다.

- `Revoke`는 해당 브라우저 세션 하나를 폐기합니다.
- `Force logout subject`는 해당 주체의 세션을 종료합니다. 위임된 관리자는 허용된 그룹 범위에서 주체 로그아웃을 수행할 수 있지만, 개별 세션 삭제와 전체 로그아웃은 직접 관리자 권한이 필요합니다.
- `Global logout`은 확인란 선택과 추가 확인창이 모두 필요합니다. 모든 브라우저 세션과 OAuth 토큰을 폐기하며 현재 관리자 세션도 끝납니다. 성공 후 다시 로그인해야 합니다.

세션 종료 후 본인 브라우저 접근도 영향을 받을 수 있으므로, 전체 로그아웃 전에 다른 운영자가 복구할 수 있는지 확인하세요. `Apply`에서 상태나 행 수를 바꾸면 현재 목록과 URL의 필터가 새 값으로 갱신됩니다.

## 이벤트 로그

`Events`에서 수준, 이벤트 유형, 시작·종료 시각, 개수를 선택하고 `Load`를 누릅니다. 날짜/시간 입력은 현재 브라우저의 현지 시각으로 표시되며 요청은 Unix 초로 변환됩니다. 기본 조회 범위는 직전 24시간이고 개수 기본값은 100입니다. 결과가 여러 페이지면 `Next page`로 이어서 봅니다. `Auto-refresh`를 선택하면 현재 필터로 5초마다 첫 페이지를 다시 조회하고, 선택을 해제하면 반복 조회를 멈춥니다.

수준은 최소 심각도 기준입니다. `All`은 빈 값으로 표시되지만 요청에서는 가장 낮은 수준인 `info`로 처리되며, 서버는 선택한 수준 이상인 이벤트를 반환합니다. 따라서 `All`/`info`는 전체 수준을 포함하고, `warning`은 warning과 critical 이벤트를 포함합니다.

오류는 상태 영역에 표시됩니다. 조회 범위나 필터를 줄여 다시 시도하고, 자동 새로고침 중에는 반복 요청이 발생하므로 점검이 끝나면 꺼 두세요.

## 이메일 템플릿 미리보기

이 화면은 이메일을 발송하지 않는 읽기 전용 미리보기입니다.

1. `Type`에서 템플릿 유형을 고릅니다.
2. 해당 유형에 사용할 수 있는 `Language`를 고릅니다.
3. 아래 iframe에서 렌더링 결과를 확인합니다. 유형을 바꾸면 이전 언어 선택과 미리보기가 지워지므로 언어를 다시 선택하세요.

유형과 언어 목록은 서버가 로드한 이메일 템플릿에서 가져옵니다. 배포는 기본 템플릿 또는 `GOAUTHY_EMAIL_TEMPLATES_FILE`로 제공된 유효한 템플릿을 로드해야 합니다. 목록이 비어 있으면 설정과 시작 로그를 운영자에게 확인하세요. 미리보기의 이메일 주소, 토큰, OTP, 만료 시각은 샘플 데이터이므로 실제 사용자에게 보내거나 실제 토큰으로 사용하지 마세요.

## IP 차단 목록

IP 차단 기능은 `GOAUTHY_IP_BLACKLIST_ENABLED=true`로 활성화된 배포에서만 사용할 수 있습니다. 비활성화된 경우 목록이 기능 비활성 안내를 표시하고 변경 입력을 잠급니다.

1. `IP prefix`에 서버가 허용하는 정규 CIDR 표기(예: `203.0.113.0/24`)를 입력합니다. 브라우저는 이를 정규화하지 않으며 서버가 표기와 주소 범위를 검증합니다.
2. `Expiry`에 미래의 만료 날짜와 시각을 입력하고 `Block IP`를 누릅니다. 만료값은 브라우저의 현지 시각에서 Unix 초로 변환됩니다.
3. 목록에서 접두사와 만료 시각을 확인합니다. 만료하지 않는 항목은 `Never`로 표시됩니다. `Remove`를 누른 뒤 확인하면 차단 항목을 제거합니다.

형식이 잘못됐거나 만료가 과거인 요청은 서버 오류로 표시됩니다. 차단 기능 활성화는 관리 화면뿐 아니라 실제 요청에 적용되는 미들웨어 배포 설정도 필요합니다. 의도치 않은 CIDR 차단은 사용자 트래픽에 영향을 주므로 적용 전 범위를 검토하세요.

## 운영 워크플로 예시

### 신규 사용자 온보딩

1. 필요한 역할과 그룹이 있는지 먼저 확인하고, 없으면 목록에서 만듭니다.
2. `Users`에서 계정을 생성하고 이메일, 언어, 역할·그룹을 지정합니다.
3. 활성화 이메일 흐름이 시작됐는지 생성 결과를 확인합니다. 사용자가 로그인한 뒤 필요하면 계정 상세에서 프로필, 만료, 사용 여부를 조정합니다.

### 퇴사자 또는 접근 중단

1. 사용자 편집에서 `Enabled`를 해제하거나 운영 정책에 따라 사용자 삭제를 진행합니다.
2. 긴급한 접근 차단이 필요하면 해당 행의 `Force logout subject`를 사용합니다.
3. `Sessions`에서 관련 세션 상태를 확인합니다. 개별 세션 폐기나 전체 로그아웃은 직접 관리자 권한과 영향 확인이 필요합니다.

### API 자격 증명 교체

1. 새 이름의 최소 권한 키를 만듭니다.
2. 한 번만 보이는 비밀 값을 복사해 소비자 서비스의 안전한 비밀 저장소에 반영합니다.
3. 새 자격 증명으로 서비스가 동작하는지 확인한 후 기존 키를 삭제합니다. 같은 이름의 `Rotate`는 기존 값이 즉시 무효화되므로 교체 창을 따로 확보할 수 있을 때 사용하세요.

### 인증 장애 조사

1. `Events`에서 문제 발생 시각을 포함하도록 범위를 설정하고 `warning` 또는 `critical`을 먼저 선택합니다. 필요한 이벤트 유형을 좁혀 조회합니다.
2. 세션 문제라면 `Sessions`에서 상태와 마지막 확인 시각을 보고, 의심 세션만 폐기합니다.
3. IP 차단이 원인일 가능성이 있을 때만 `IP Blacklist`를 확인하고 해당 접두사와 만료를 검토합니다.

## 실패 시 확인 순서

1. 로그인 세션이 유효한지 확인하고 페이지를 새로 고칩니다. 관리자 UI가 시작 단계에서 CSRF 토큰을 얻지 못하면 운영자가 issuer-bound CSRF 제공 구성을 확인해야 합니다.
2. 해당 화면의 오류 문구, 대상 ID/이름, 선택한 범위를 기록합니다. 폼 입력이 유지되면 재전송하기 전에 값을 검토하세요.
3. `401` 또는 `403`이면 로그인 세션, CSRF 검사, 계정에 필요한 읽기/변경 권한을 함께 확인하세요. 관리자에게 권한 범위를 확인하세요. API 키 관리 화면에는 API 키 권한만으로 접근할 수 없습니다.
4. `404`는 대상이 없거나 기능이 배포에서 꺼져 있는 경우일 수 있습니다. 특히 IP 차단 목록은 기능 비활성 시 라우트가 등록되지 않습니다.
5. `503`은 서비스 구성 또는 백엔드 일시 장애일 수 있습니다. 사용자 생성이면 복구 서비스 설정을, 템플릿 미리보기면 템플릿 제공자 구성을 운영자에게 확인하세요.
6. 관리 화면은 일부 오류 응답의 본문을 그대로 보여 주므로 영어 문구가 나타날 수 있습니다. 비밀 값은 오류 화면이나 티켓에 복사하지 마세요.

## 검증 근거와 범위

- **실제 API/서버 계약:** 이 안내서의 경로와 제약은 `cmd/goauthy/main.go`, `internal/rbac`, `internal/apikey`, `internal/ipblacklist`, `internal/admin/ui.go`의 라우트·핸들러를 확인해 작성했습니다. 관련 Go 테스트는 서버 권한 검사, 요청 형식, 저장 계층의 별도 증거입니다.
- **모의 UI 검사:** `docs/ui-audit-admin-core.md`와 `docs/ui-audit-admin-modules.md`가 설명하는 Node 테스트는 DOM과 네트워크 경계를 mock으로 실행합니다. 폼의 요청 경로·본문·일부 오류 표시를 확인하지만 실제 브라우저 배치나 배포 상태를 증명하지 않습니다.
- **기록된 라이브 검사:** `docs/admin-ui-implementation.md`에는 `TestAdminUIHTTPAcrossPods`의 HTTP 검증과 `TestAdminUIBrowserAcrossPods`의 standalone Chromium 사용자·역할·그룹 흐름이 통과했다고 기록되어 있습니다. API 키 관리의 rotate/delete는 브라우저 세션+CSRF를 쓰며 `Authorization: API-Key`는 서버가 거부합니다. 수정된 live HTTP lifecycle 검사는 session+CSRF rotate/delete 성공과 API-key 거부를 localhost에서 통과했으며, HA/다중 노드 결과는 아직 없습니다. 앞서 `403` 본문이 비어 있는데도 나온 `changed=true`는 회전 증거가 아닙니다. 이 안내서 작성 과정에서는 브라우저나 E2E를 실행하지 않았으므로 기존 기록을 새로 재검증한 것으로 보지 마세요.
