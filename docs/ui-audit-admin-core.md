# Admin core UI/API audit

Scope: dashboard plus users, roles, groups, and API keys in `internal/admin/admin.js`. The browser uses the existing same-origin session and fetches `/auth/v1/admin/csrf` before routing. Mutations add that token as `X-CSRF-Token`; the server performs the authoritative session, CSRF, and permission checks. The UI’s `api()` helper sets pending state around mutations, preserves non-empty text HTTP error bodies, and restores pending state in `finally`.

## Findings and limits

- **Metadata parse errors:** the admin UI localizes malformed JSON feedback while retaining the backend’s existing support for valid JSON objects, arrays, strings, numbers, booleans, and null. Existing false/zero metadata also remains visible in the edit form.
- **User creation is deployment-dependent:** `POST /auth/v1/users` is registered only when `recoveryService` is configured. The UI still exposes the create route; deployments without that service receive `503 Service Unavailable`.
- **API-key rotation E2E 403 is a test-contract mismatch:** `internal/apikey/http.go` makes key management browser-session/CSRF-only and rejects Authorization-header API-key principals. The admin UI correctly calls the `/secret` route with same-origin credentials and CSRF. Comparing the empty 403 body with the old secret can yield `changed=true`; it is not proof of rotation. The parent task is updating the cross-pod test to use a browser session plus CSRF and assert API-key denial; backend behavior remains unchanged.
- **Backend error text is not localized:** `api()` preserves useful text/plain bodies and JSON `error` values (or status text) for diagnosis, so these may appear in English. The local metadata parser error is translated. Localizing arbitrary service errors requires a stable error-code mapping from the API.
