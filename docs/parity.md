# Rauthy v0.36.2 behavior-parity plan

## Fixed baselines

- Product behavior: [Rauthy v0.36.2](https://github.com/sebadob/rauthy/releases/tag/v0.36.2), commit `dd61ac3c84d6b238108dc8438b53043b5177a662`.
- Database: official [Rhiza v0.12.3](https://github.com/mrchypark/rhiza/releases/tag/v0.12.3), commit `97a9d18aadc66d3b5390f6fa64de2d65dd9f0d48`. Rhiza v0.10.0 remains the historical baseline for earlier recorded runs.
- Database runtime companion: official LatticeDB v0.5.1; the Go integration requires neither cgo nor a Rust SDK.
- Rauthy README/Book `main` content is evidence for current upstream only. Features not proven in the fixed tag remain an upstream-delta item.
- Explicit scope substitution from the project goal: Rhiza is the only runtime backend. Rauthy's Hiqlite/Postgres migration is therefore not claimed as parity; GoAuthy remains behavior-parity with this documented backend exception.
- `[x]` requires implementation plus a deterministic test. Security and HA rows also require a negative or fault test.

Current qualification (2026-09-17): all six audit gates PASS — P0 security autolink guards + creator race, P0 compile+normal/vet, P1 upstream MFA, P1 admin mapping+profile, P1 actual new E2E+schema, P2 full production race (all 61 packages) + Kind V4 E2E + MinIO S3 recovery. Schema v102. Broad Rauthy behavior-parity goal remains paused; event-hash runtime unimplemented.

Current source and dated execution evidence are summarized in [status.md](status.md).
The concrete user CRUD contract and pending atomicity/E2E gates are in
[user-management.md](user-management.md). The guarded list and deterministic
pagination are implemented. Detail target authorization and existing-state projection
are wired, but missing lifecycle/profile state keeps full detail unchecked;
administrator creation now has the guarded DTO/membership/password-new flow,
but creation events/SCIM/UI and full update remain unchecked. The
opaque cursor deliberately supports legacy zero timestamps and GoAuthy IDs,
with stable same-time ordering; it is not the original raw timestamp+ID format.
Schema 58 adds nullable account deadlines, request/transaction guards, and
token-endpoint access/refresh/ID lifetime caps including exchange actors.
Final-submission snapshot guards reject even still-future deadline shortening;
response state is rechecked after commit/signing. JWT caps round down to seconds.
The bounded expiry worker now performs conditional atomic disable/revocation,
durable backchannel enqueue and optional guarded retention deletion; existing
SCIM reconciliation projects retained disabled users. PAM and full management
reactivation remain open. See the explicit batch/HA/convergence adaptations below.
Code/PKCE caps now share account snapshots; current OAuth token consumers recheck
owner/actor eligibility while preserving explicit revocation and refresh reuse.
Its exclusive millisecond boundary is stricter than upstream's seconds-based
request check; full expiry lifecycle and live gates remain explicitly open in
[user-management.md](user-management.md).
Earlier focused geoblock/login-policy/IP-blacklist, command authority and
token-metrics tests passed at count 3. Historical low-disk/inotify failures
below are not claims about the current host. Each named Kubernetes result is
limited to that profile. Keep upstream-provider broader parity and Kind E2E/chaos evidence
unchecked; its runtime is source-wired. Automatic failed-login blacklist
admission is source-wired and focused-tested, while broader DoS remains unchecked;
geoblock admission is source-wired and its standalone and exact-three trusted-
header gates pass all-pod admission, pod-1 replacement, and trust-boundary
spoof denial. The header source requires trusted proxies; local MaxMind is the
alternative source, raw database values are strict ASCII ISO alpha-2, and
allow/deny/unknown decisions are fail-closed as configured. MaxMind success
fixture coverage now includes standalone and exact-three HA runtime checks;
no downloader or update scheduler exists.
With the current Rhiza v0.12.3 integration, startup failure paths still
intentionally skip `db.Close()` until all startup initialization succeeds; the
startup-close workaround remains pending verification against the upgraded runtime;
normal post-start shutdown still closes the database as usual.

Bootstrap authentication is password-only for the initial administrator by
default; passkeys are optional. `GOAUTHY_BOOTSTRAP_FORCE_MFA=true` is an
explicit opt-in that fails startup unless the complete passkey configuration is
valid, rather than falling back to password-only login. Forward Auth identity
headers are independent of passkey configuration: when
`GOAUTHY_FORWARD_AUTH_HEADERS=true` and passkeys are disabled,
`X-Forwarded-User-MFA` is emitted as `false`. See the
[bootstrap passkey policy](passkey-bootstrap.md).
DCR `last_used` updates for successful `PUT` and dynamic token issuance are
verified source behavior (monotonic commit-time timestamps); excluded grant
and failure paths remain intentionally unsupported.
Master-key envelope maintenance is source-wired through a minute worker that
independently cursor-scans bounded signing-key, live DCR-idempotency, and
unexpired upstream-transaction rows, authenticates old envelopes, and performs
exact CAS rewraps under the active key. OAuth persisted request forms redact
credential, bearer, and one-use fields while retaining non-secret protocol
metadata. Full critical-DB encryption remains unchecked: nonrotating values,
automatic key removal and CookieKey removal are still pending. Master-key retirement Stage A
prepare, Stage B commit fencing, and Stage C runtime admission/attestation/
ready/abort are implemented; successful guarded transitions append exactly-once
audit events in the same Rhiza transaction. Deterministic standalone exact-one
and exact-three state-machine/replay/revocation-interposition/chain-integrity
tests cover the source contract; the live exact-three gate passed all three
zero-reference checks, restart boot-ID change with attestation sequence 2,
Ready, key retention, and cleanup. No automatic key removal exists.

Rhiza schema v102 is the current source baseline (v98-v102: scim_client_config, force_mfa, system_lockdown, identity_email_otp, event_log prev_hash/integrity_hash). The schema-v38 provider-scoped
SCIM remote-user mapping, user-first full scan/reconcile, group enqueue/runtime,
and schema-v39 tombstone/delete projection are source-tested. `identity.DeleteUser`
atomically snapshots a tombstone, cleans owned identity state, invalidates stale
user-sync outbox rows, and durably enqueues SCIM delete work. `sync_delete_users`
defaults to RFC 7644 unlink and opts into hard DELETE when true; explicit user
deletion always uses hard `DELETE` independently. Production admin/self deletion
routes are source-wired with exact browser/API-key/CSRF/default-off behavior;
encrypted per-client configuration remains unverified. After a bounded drain,
tombstone cleanup removes oldest tombstones only when exact delete jobs for
every snapshotted provider have succeeded; hard local deletion requires
`DeleteRemote`, pending/processing/dead/missing jobs retain the
tombstone, and terminal delete outbox rows remain while their tombstone exists.
Schema v41 snapshots immutable deletion-time provider IDs and policies. Legacy
v39/v40 tombstones have incomplete snapshots and are never auto-cleaned. A
removed provider blocks cleanup until the same stable ID returns; new providers
receive no historical deletes. Schema v42 adds opaque 128-bit/22-character
base64url tombstone generations and a Rhiza-atomic exact-generation enqueue
fence, so a stale pod cannot delete a recreated subject. Empty generations,
incomplete snapshots, and malformed hard-delete snapshots fail closed; legacy/raw/no-generation delete rows are
unclaimable. Complete empty-generation tombstones are retained and skipped
without blocking later work. The generation is persisted inside delete-job JSON,
and both claim and cleanup require an exact current generation. Dead-letter
retry is operator-controlled and provider re-add alone does not revive dead
jobs. The client supports optional per-provider `ca_file` roots via stdlib
`x509.CertPool`, with hostname verification, TLS 1.2+ minimum, no proxy, and
no `InsecureSkipVerify`; a deterministic TLS fixture covers this boundary.
Transport/DNS/TLS/drop failures and `429`/`5xx` retry, while malformed/permanent
`4xx` responses are dead-lettered. Standalone and exact-three HA semantics are
identical, and HA pods must use matching provider configuration.

open-registration ordinary users, self/admin deletion, old-session and relogin
denial, replay `404`, final-admin `409`, UID-verified pod replacement/readiness,

cross-pod session/token invalidation, final-admin protection, pod-0 replacement,

user-delete/full-SCIM profile remains unverified; no full SCIM parity claim is
made. The
exact-three Kind harness passes source/static checks but live execution stops at
Docker inotify `128<256`, so no HA runtime claim is made. The worker is
production-wired, but the full SCIM feature remains unchecked.
FedCM has strict default-off
production source wiring via `GOAUTHY_FEDCM_CONFIG_FILE`: HTTPS-only config,

`/auth/login` or `/auth/v1/account` password landing, active identity+peer

## Direct implementation record

Direct code is allowed only when the protocol or product policy is not owned by a suitable maintained package. Cryptographic primitives are never reimplemented.

| Area | Research result and reason direct code remains |
|---|---|
| Rhiza persistence | Rhiza exposes its own Go API and JSON/HTTP adapter, not `database/sql`. OAuth grants, sessions, replay state, migrations and ambiguous-write reconciliation therefore need a GoAuthy-specific adapter. Every mutation keeps a stable request ID for one logical retry, with a fresh attempt ID after an authorization guard deliberately produced no command effect. The earlier follower `no such savepoint: rhiza_command` symptom was traced to SQLite needing a writable temp path while the restricted main container had `readOnlyRootFilesystem`; `/tmp` is now an `emptyDir` and `SQLITE_TMPDIR=/tmp`. The final full three-node gate passed RBAC claims/rename/refresh/replacement and the listed protocol/fault slices after that correction; this still does not prove untested parity work complete. |
| Rhiza SQL binary values | Official Rhiza v0.10.0 serializes `[]byte` inside SQL `[]any` arguments through JSON without a binary type tag, so a STRICT BLOB column receives TEXT and rejects the write. Encrypted envelopes are therefore stored as raw-base64url TEXT; decoded bytes remain authenticated by AES-GCM. Revisit if Rhiza adds typed SQL arguments. |
| OAuth/OIDC product behavior | Fosite is an OAuth2/OIDC framework, not an IdP. Login, authorize-directive, claims, client policy, device UI, session semantics and missing extension endpoints remain application behavior. |
| Fosite v0.49 gaps | The pinned release has PAR but no logout, DCR, device or DPoP server handlers; unreleased `master` device code is not a dependency. Its ID-token path uses `go-jose/v3`; raw Ed25519 signing works but parts of signer validation only recognize RSA/ECDSA. Keep existing `go-jose/v4` at the public JWKS boundary and require an EdDSA sign/verify/JWKS round-trip before choosing a narrow adapter instead of ES256. |
| Fosite request-state race fix | Shared mutable verifier/token state was the race root under concurrent authorization requests. ## Rhiza security and consistency rules

- Use only the public Go API in-process. The optional Rhiza HTTP adapter has no client authentication or TLS and must not be exposed.
- Target HA topology is exactly three GoAuthy StatefulSet pods embedding Rhiza v0.12.3. Each has a unique node ID and disposable emptyDir, distinct voter token, fixed ordered membership and shared object storage. GoAuthy has no PVC. Object storage must survive loss of application disks; MinIO fixtures and physical-host independence have separate limits. See [no-PVC DR contract](no-pvc-dr.md) for before-ack durability, tests and deployment constraints.
- The executable supports standalone (one embedded member) and exact-three-member cluster profiles. Production no-PVC manifests require object storage in both profiles. Standalone accepts object-store/checkpoint settings and rejects peer settings; dev rejects object-store/peer settings. Changing replica count requires revisiting the architecture.
- Security decisions read with `ConsistencyLinearizable`; losing quorum must fail closed and never fall back to local stale data.
- Generate IDs, timestamps and secrets in Go and bind arguments. Replicated SQL rejects nondeterministic SQL functions and explicit transaction control.
- OIDC Ed25519 seeds are encrypted with AES-256-GCM under a mounted master-key keyring. Issuer, signing `kid`, algorithm, envelope version, master-key ID and nonce are authenticated as AAD; a decryption or thumbprint mismatch fails startup/readiness and never generates a replacement.
- The runtime rewrap worker independently scans signing-key, live DCR-idempotency, unexpired upstream-transaction, and retained passkey DB envelopes in bounded cursor batches, authenticates before mutation, and uses all-or-zero exact old-row CAS under the active key. OAuth persisted request forms drop credential, bearer, and one-use material while retaining non-secret protocol metadata. Master-key retirement Stage A prepare, Stage B commit fencing, and Stage C runtime admission/attestation/ready/abort are implemented; successful guarded transitions append exactly-once audit events in the same Rhiza transaction. Deterministic standalone exact-one and exact-three state-machine/replay/revocation-interposition/chain-integrity tests cover the source contract. Live exact-three gate `KIND_CLUSTER=goauthy-master-key-e2e-20260905c E2E_PORT=19700` passed three zero-reference checks, restart boot-ID/sequence 2, Ready, key retention, and cleanup; automatic key removal, Passwordless CookieKey rotation, and remaining nonrotating values remain unverified.
- GoAuthy policy caps each `ExecuteRequest.Statements` transaction at 64 statements; Rhiza v0.10.0's internal `MaxSQLStatements` limit is 128. Never send raw SQL batches.
- `ErrCommitUnknown` is reconciled with the same request ID or `RequestStatus`; a new ID can duplicate a security mutation.
- The earlier follower savepoint symptom was caused by the restricted main container lacking a writable SQLite temp directory. The deployment now provides `/tmp` through `emptyDir` and exports `SQLITE_TMPDIR=/tmp`; the final full kind gate passed its RBAC claims/rename/refresh/replacement slice and listed protocol/fault checks. This is not a global parity-completion claim.
- Rhiza v0.10.0 is a clean-install development release. It explicitly lacks legacy storage migration compatibility, recovery-certificate signing/key rotation and peer mTLS.
- Rhiza v0.10.0 formally exposes `DB.Ready`, `ValidateExecuteRequest`, a 128 KiB replicated mutation limit, and a distinct 1 MiB optional-HTTP body limit. It also adds bounded graph reachability APIs, which GoAuthy does not need or use. Existing `Open`/`Ready`/`Query`/`Execute` APIs remain compatible, as covered by successful local tests. GoAuthy validates mutations locally before submission and combines local recovery readiness with a linearizable schema query; `DB.Ready` alone is not a quorum probe.
- Do not depend on mutation `RETURNING` rows: v0.9.0 explicitly documents receipt-only replicated mutations. Write with a stable request ID, then perform a linearizable query.
